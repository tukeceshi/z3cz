# 修复:轮询成功但节点一直"生成中"(全链路审查结论)

## 根因(审查确认)
1. **面板提交后没有"收尾"**:字幕擦除面板拿到 jobId 后只写了 generating metadata 就结束;而裁剪的同款流程(runCloudTrim)在提交后会继续 **claim 任务 → resolveCloudGenerationJobMedia 下载/上传 → finalize → persistMediaForNodeInBackground → 写终态 metadata(历史项+清除生成中标记)**。我们缺了这一整段。
2. **恢复宿主无法兜底**:兄弟节点的 `GenerativeCloudJobResumeHost` 的 autoResume 读取的是**挂载时捕获的 jobId 引用**(useRef 初始值),而我们的 jobId 是节点创建之后才写入 metadata 的 → 宿主不会触发恢复(宿主设计用于页面刷新后恢复,那时 metadata 已带 jobId,场景不同)。
3. **服务端超时兜底只救了媒体、救不了节点**:ready_to_persist 超时后 runServerGenerationJobPersist 会把媒体持久化(所以你看到轮询成功/媒体已就绪),但没有任何代码去更新兄弟节点的 metadata → 卡片永远"生成中"。

## 修复方案(镜像裁剪 runCloudTrim 的收尾段)
`ai-video-subtitle-erase-config-panel.tsx` 的 handleGenerate,在拿到 `response.jobId` 后继续执行:
1. 写 `{ jobId, phase: "generating" }` metadata
2. `tryClaimGenerativeJobResume(jobId)`:
   - 抢到 → `resolveCloudGenerationJobMedia({ organizationId, jobId, workflowId, cloudConfigured, onProgressPhase })`,onProgressPhase 把 downloading/uploading 阶段写进兄弟节点 metadata
   - 没抢到 → while 轮询 `getGenerationJob` 直到 succeeded(finalMedia)/failed/cancelled,间隔 VIDEO_JOB_CLIENT_POLL_INTERVAL_MS
   - finally `releaseGenerativeJobResume(jobId)`
3. media 为空 → 抛错(走既有 catch 写错误 metadata)
4. `tryClaimGenerativeJobFinalize(jobId)` → 抢到则 `persistMediaForNodeInBackground({ media, nodeType: "ai-video", ... })`
5. 终态 metadata(与恢复宿主成功路径一致):`appendAiVideoGeneratedHistoryItems`(params 记录本次配置、jobId)+ `clearGenerativeProgress` + 生成标记 false + 清除错误;未抢到 finalize 则仅清进度。成功 toast
6. 新增导入:tryClaimGenerativeJobResume / releaseGenerativeJobResume(已有 registry)、resolveCloudGenerationJobMedia、getGenerationJob、VIDEO_JOB_CLIENT_POLL_INTERVAL_MS、appendAiVideoGeneratedHistoryItems、本地 sleep

## 不改的部分(审查确认无需动)
- 服务端 poll/service/路由(轮询本身工作正常)
- 恢复宿主(其职责是页面刷新后恢复,设计如此)
- 服务端超时兜底(保留作为浏览器中途关闭的安全网;刷新后 metadata 带 jobId,宿主可恢复)
